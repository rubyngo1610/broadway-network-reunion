# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A course project (NYU DS-GA 3001) studying how Broadway musical creative teams form, disperse and reunite. Two parts:

1. **A Python data pipeline** (`scripts/`, `src/`, `config.py`) that builds the dataset from **Wikidata SPARQL and English Wikipedia only** (IBDB is not available as a source).
2. **Static D3 web views** (`viz/`) that read JSON exported by the pipeline and are published to GitHub Pages.

`README.md` (pipeline, data dictionary, Wikidata IDs) and `viz/README.md` (views, JSON formats) are detailed and current. Read the relevant section before changing a step's outputs. `WORKLOG.md` is the decision record. Add an entry there (newest at the bottom) for every full run, every code change that affects outputs, and every manual edit to a review file.

## Commands

There are no tests and no linter. Each step is verified by running it on a small sample.

```bash
source ~/venvs/broadway/bin/activate        # venv lives outside the repo (the repo may sit in Google Drive)
export BROADWAY_DATA_DIR=~/broadway-data    # data/ lives outside the repo too; config.DATA reads this

python scripts/05_merge_resolve.py --limit 20 -v   # any step: --limit N (first N shows), --refresh (ignore cache), -v
python scripts/13_export_viz_data.py               # rewrite viz/data/*.json after rerunning 05, 08 or 09

cd viz && python3 -m http.server 8000              # the views use fetch(), so they must be served over HTTP
```

Steps run in numeric order: 01 → 02 → 03 → 04 → (04b, optional) → 05 → 06 → 07 → 08 → 09 → 13 (→ 14, basemap, rarely needed). Steps 10–12 are the methods: 10 is `scripts/10_null_model.py` (the H1 null model), 11 is `scripts/11_bigclam.py` (BigCLAM per window), and 12 is community tracking (not built yet). See the latest `WORKLOG.md` entries. Step 11 can run without pipeline data, because `--source json` reads `viz/data/credits.json`, which matches step 08's `person_show.parquet`; try it with `--modes strict --cutoffs 1950 1980`. Step 15 (`scripts/15_h3_prediction.py`, the H3 prediction test) reads step 11's output. Both steps take their loaders and window graphs from `src/network.py`. A typical rerun after changing resolution or filters is **05 → 06 → 08 → 09 → 13**.

## Architecture

- **Every network call goes through `src/http_client.py`.** It only allows the two hosts in `config.py`, rate-limits, retries (honoring `Retry-After`), and caches every response under `data/raw/`. Reruns are therefore offline unless you pass `--refresh`. Don't add direct `requests` calls in pipeline code. `utils/resolve_via_ibdb.py` is an older exception that bypasses the cache. The one other exception is step 14's basemap sources (Overpass, NYC Open Data).
- **Scripts share a skeleton through `src/common.py`**: `parse_args` (the standard flags), `apply_limit`, and `read_parquet`/`write_parquet` (writes are atomic). All paths come from `config.py`.
- **Wikidata IDs are verified at run time.** `src/wikidata.py` checks the live English label of every P/Q ID it uses and aborts on a mismatch. A new ID must be added to that verified list and to the README table.
- **Data flow:** shows (01) → Wikidata credits + people (02) → wikitext (03) → infobox and prose credits (04) → merge and person resolution (05) → `data/processed/{credits,people,shows}.parquet` → network windows and reunion labels (08, `data/processed/network/`) and opening theatres (09, `data/processed/venues/`) → `viz/data/*.json` (13).
- **Nothing is dropped from `data/`.** Filtering happens downstream. The **core show set** is defined in `src/filters.py` (hand-checked lists `NEVER_ON_BROADWAY`, `OPERAS`, `MANUAL_EXCLUDE`, plus `CORE_MIN_YEAR`), and `outputs/tables/show_set.csv` records each show's `exclusion_reason`.
- **Roles** use a fixed vocabulary in `src/roles.py`. Network settings (roles, window W, horizon H, cutoff years, posthumous grace) are in `config.py` and were fixed before looking at results. Network modes: `strict` (only credits confirmed as original production) and `loose` (also unknowns). Views default to `strict`.

## Hand-curated files (don't regenerate or overwrite them)

- `outputs/tables/manual_name_resolutions.csv`: the permanent manual person resolutions. Step 05 reads this file but never writes it, and its entries win over `unresolved_names.csv`. `unresolved_names.csv` is rewritten on every run, so fixes made only there get lost. Put new name fixes in the permanent file.
- `outputs/tables/spotcheck*.csv`: answered spot-checks. Step 07 refuses to overwrite one unless you pass `--force`. Score a spot-check with `python scripts/07_spotcheck_sample.py --score`.
- `VENUE_OVERRIDES` and `NON_BROADWAY_QIDS` in `scripts/09_show_venues.py`: fixes for show → theatre assignments.
- `viz/data/*.json` is generated by step 13 (and `basemap.json` by step 14). Don't edit these files by hand.

## Web views (`viz/`)

- No build step and no npm. D3 is pinned at `d3@7.9.0` from jsDelivr, and the code uses native ES modules.
- `js/main.js` routes on the URL hash (`#showmap` is the default; parameters go after `?`, e.g. `#showmap?year=1927`). Each view in `js/views/` exports `render…(el, db, params)`.
- `js/data.js` `loadData()` builds one shared `db`: the raw tables, lookup maps (`showById`, `creditsByPerson`, …) and helpers. It also expands the compact rows in `reunions.json`.
- `js/manhattanMap.js` is the shared zoomable map. It is rotated 29° to grid north, and views re-place their dots on every zoom, so dots keep a constant screen size.
- Styling is done through CSS custom properties in `css/style.css`, with light and dark modes. Change the tokens rather than per-view colours. Gold marks reunions and highlights and is never used for body text (use `--accent-ink` for text).
- `.github/workflows/pages.yml` deploys `viz/` on every push to `main` that touches `viz/**`.
